Why FastBallMapper is faster than pyballmapper

For identical inputs, FastBallMapper produces a bit-for-bit identical graph while running 20–36× faster. This page explains why — through the algorithmic changes and measured numbers — and then summarises GPU / multi-core extension options and alternative algorithms that would change the output.

One-line summary

Almost all of the speed-up comes from algorithmic replacements. Specifically: (1) the O(N²·D) direct distance loop is replaced by a BallTree, and (2) the per-pair Python set.isdisjoint loop is replaced by a sparse matrix product (SpGEMM). Multi-core parallelisation shaves off an extra 1.2–1.6×, but compared to the algorithmic gain (~20–30×), that is a secondary effect.

Per-phase algorithm comparison

The BallMapper build process splits naturally into 4 phases. For each phase we compare the data structure / algorithm used by pyballmapper (reference) and by FastBallMapper.

Phase Role pyballmapper (reference) FastBallMapper Complexity change
1. Build index Prepare a data structure for distance queries None (linear scan) Build sklearn.neighbors.BallTree once O(N²·D) → O(N·D·log N) once
2. Landmark selection Greedy ε-cover selection For every candidate, compute distance to all existing landmarks covered boolean mask + single-point query_radius O(N·L·D) → O(N + L·log N·k̄)
3. Coverage Set of points covered by each ball Recompute every point–landmark pairwise distance Batched query_radius (Cython, GIL-released, threading) O(N·L·D) → O(L·log N·k̄) [parallel]
4. Edge finding Add an edge if two balls share at least one point Double loop + Python set intersection Sparse incidence M, computed as M @ M.T O(L²·k̄) → O(L·k̄²) C++ SpGEMM (no GIL)

N = number of data points, D = dimension, L = number of landmarks, k̄ = mean ball size. On the benchmark data (N=20000, D=100), L ≈ 236–3761 and k̄ ≈ 60–100 depending on eps.

Key insights

  • Phases 1 and 3 are unified behind a single data structure — BallTree. Being Cython-based, it releases the GIL, which lets the threading backend actually parallelise.
  • Phase 4 reframes "do these two sets share an element?" as "do these two rows have a 1 in the same column?", reducing it to a matrix product — a single C++ SpGEMM call ends it.
  • The greedy decision order in Phase 2 is preserved → the output is bit-for-bit identical.

Why parallelisation has a ceiling

Amdahl's law

The reason total speed-up stays within 1.07–1.64× even on 8 cores is simple — the serial phases are too large. Take the eps=0.04 case: 

At n_jobs=1 (total 2.37s):
  build_tree         ≈ 0.05s   (serial, Cython BallTree)
  landmark_selection ≈ 1.24s   (serial, greedy)
  coverage           ≈ 1.07s   (parallelisable)
  edge_finding       ≈ 0.005s  (single C++ SpGEMM)

Serial fraction = (0.05 + 1.24) / 2.37 ≈ 54.5%
Theoretical upper bound (Amdahl) = 1 / 0.545 ≈ 1.83×
Measured (8 cores)               = 1.07×    (≈ 59% of the bound)

The remaining 41% is eaten by joblib pool startup cost, per-chunk BallTree call overhead, and thrashing on 8 cores (measured std is ±0.26s — large).

GIL trap: why the old edge_finding could not be parallelised

Before SpGEMM was introduced, edge_finding ran a loop like the following under backend="threading": 

for u in candidate_neighbors[v]:
    if u > v and not cov_sets[v].isdisjoint(cov_sets[u]):
        ...

set.isdisjoint is implemented in C inside CPython but does not release the GIL. So even with 8 threads on the threading backend, only one can run at a time → measurements were 0.20×–0.85×, i.e. actually slower (only joblib overhead was added). After SpGEMM, the entire phase finishes in ~3 ms via one C++ call, making the parallelisation question moot.

SpGEMM edge_finding — concrete application

Idea

If each landmark's coverage is represented as a sparse 0/1 incidence matrix, then the intersection size of two balls is simply the dot product of two rows. To compute every pair at once, one matrix product is enough: 

M ∈ {0,1}^(L × N)    where  M[v, p] = 1  iff  point p ∈ ball v
S = M @ M.T          where  S[v, u] = |cov(v) ∩ cov(u)|

edge (v, u)  ⇔  S[v, u] > 0   (and v < u)

The triangle-inequality prefilter is automatic — if two balls lie more than 2·ε apart, then cov(v) and cov(u) are disjoint, so the corresponding entry of the sparse product is zero. The cost of building a second BallTree disappears.

Implementation

indptr = np.empty(L + 1, dtype=np.int64)
indptr[0] = 0
np.cumsum([len(arr) for arr in coverage_arrays], out=indptr[1:])
indices = np.concatenate(coverage_arrays).astype(np.int64, copy=False)
data    = np.ones(int(indptr[-1]), dtype=np.int32)

M = csr_matrix((data, indices, indptr), shape=(L, N))
S = (M @ M.T).tocoo()
mask = S.row < S.col
all_edges = list(zip(S.row[mask].tolist(), S.col[mask].tolist()))

References — how to push further

1. If slightly different output is acceptable — alternative landmark-selection algorithms

FastBallMapper currently guarantees bit-for-bit identical output to the reference. Relaxing this constraint allows Phase 2 (serial greedy) to be replaced by faster or more uniform cover schemes. However, analytical results (especially the topology of the mapper graph) may change, so domain validation is required.

(a) Farthest-Point Sampling (FPS) / k-center greedy

  • At each step, select as a new landmark the point that is "farthest from any current landmark".
  • Pros: more uniform cover, deterministic (given a seed), fast GPU implementations exist (PyTorch3D sample_farthest_points, Open3D, NVIDIA cuVS).
  • Cons: produces a different landmark set than greedy ε-cover. The resulting graph's node count and structure change.
  • Best when: topological analysis only cares about the mapper graph's shape and an exact landmark mapping is not needed.

(b) Leader clustering (BIRCH-style)

  • A single sequential scan: assign each point to the first leader whose ball it falls into; create a new leader if none does. O(N·L) 1-pass.
  • Pros: extremely fast, memory-efficient, results are essentially the same as greedy (only the order dependence differs).
  • Cons: fast even without a BallTree, but the sklearn implementation is not standardised (you write your own or wrap BIRCH).
  • Best when: prototyping fast, and order dependence is acceptable.

(c) Block-parallel greedy (Luby-style MIS)

  • Partition points into blocks; in parallel within each block, mark "independent" landmark candidates → resolve conflicts → next round. An application of probabilistic maximal-independent-set algorithms.
  • Pros: real multi-core parallelisation. cuGraph offers a GPU MIS.
  • Cons: each run yields a different landmark set (randomness). It is reproducible for fixed data/seed but requires comparison validation.
  • Best when: very large N (>10⁶), where the serial nature of greedy must be broken.

All three approaches require "the analytical results are essentially the same as the greedy ε-cover" domain validation before being safe. Once validated, Phase 2 itself can be moved to parallel/GPU, breaking through the Amdahl ceiling (~1.8×).

Practical guidelines

  • At current data scale, GPU yields little or no benefit. At N=20000, D=100, the CPU BallTree behaves cache-friendly, while GPU transfer + kernel launch overhead (cupy.asarray, ~tens of μs per launch) is larger than the phase time itself.
  • The crossover is roughly N·D ≥ 10⁶–10⁷. Higher D defeats BallTree pruning (curse of dimensionality, efficiency drops sharply from D≳50), making GPU brute-force progressively more favourable. At D=600, GPU pulls ahead even at N~10⁴.
  • FAISS-GPU's range_search is limited even in the latest versions (≥1.8). Restrictions on index types (only partial support for Flat) and on result buffer size. For exact radius queries, it is safer to do brute-force kNN with GpuIndexFlatL2 using a sufficiently large k and then threshold-filter.
  • cuML NearestNeighbors(algorithm='brute') is the cleanest drop-in. radius_neighbors returns a sparse CSR, so Phase 3's output can be fed directly to the SpGEMM (with CuPy, Phase 4 can also be done on the GPU).
  • Greedy Phase 2 cannot be GPU-accelerated. If you can change the output, replace it with FPS (cuVS / PyTorch3D) — very fast.

Suggested stack (for large-scale data)

Phase 1 + 3:  cuML NearestNeighbors(algorithm='brute')
              → radius_neighbors(landmarks, eps)
Phase 2    :  Keep on CPU (greedy, serial). If output may change, cuVS FPS.
Phase 4    :  CuPy sparse:  cupyx.scipy.sparse.csr_matrix.dot(M.T)
              Limit output size with a prefilter mask (S_candidate).
Phase 5    :  CPU NetworkX (small).

This stack starts to matter from N ≥ 10⁵, and around N ~ 10⁶ one can expect 5–15× over 8-core CPU and 20–100× over a single core (vendor-benchmark figures; actual measurement required).

3. What more can be squeezed out of multi-core CPU

Now that SpGEMM is in place, the serial phases (build_tree + landmark_selection) are the bottleneck. Reducing or parallelising this serial portion relaxes the Amdahl limit.

(a) landmark_selection — bulk query, then update mask

  • Now: tree.query_radius(X[i:i+1], r=eps) is called per point (L sklearn entry costs).
  • Improvement: do one batched query up front to get all point-to-point ε-neighbours (OpenMP inside Cython). The subsequent greedy loop becomes a pure-Python boolean-mask update — C-level speed.
  • Caveat: memory cost (the full neighbour list is ~O(N·k̄)). If too large, do batched calls in chunks.
  • Expected effect: lmsel 1.24s → 0.2–0.3s (~5×). Reducing the serial fraction also raises the Amdahl ceiling.

(b) coverage — drop chunking or rely on sklearn's internal OpenMP

  • The latest sklearn (≥1.3) BallTree.query_radius supports internal OpenMP parallelism. Multi-core works even from a single call, without joblib chunking. Chunk splitting can actually increase cache misses.
  • Improvement: leave n_jobs=None at the call site and control the OpenMP thread count via threadpoolctl.

(c) edge_finding — already SpGEMM; what else?

  • scipy.sparse SpGEMM is single-threaded C++. Faster options:
    • MKL Sparse BLAS (Intel MKL's mkl_sparse_spmm): multi-threaded. Wrappable via the sparse_dot_mkl package.
    • New SpGEMM in scipy ≥ 1.13: 2–3× faster in some cases than the current. You get the benefit automatically after checking the version.
  • Currently ~3 ms, so the ROI for further optimisation is low. That said, it does matter once L gets above 10⁵.

(d) NetworkX graph construction — expensive at large L

  • For L > 10⁴, nx.Graph().add_edges_from(...) itself takes non-trivial time. If breaking the pyballmapper API is acceptable:
    • python-igraph: C-based, 10–100× faster graph build.
    • Keep a simple dict adjacency list and let the caller perform whatever operations they need.

(e) Data memory / cache friendliness

  • Currently X is force-cast to float64. Keeping it as float32 makes BallTree distance computation more SIMD-friendly (sklearn supports float32 natively). Worth measuring at D≥100, where memory bandwidth is the bottleneck.
  • Pre-sorting points in a spatially friendly order (e.g. Morton/Hilbert) improves BallTree cache efficiency. To preserve identical output to the reference, however, the landmark order (= input point order) must be left untouched.
